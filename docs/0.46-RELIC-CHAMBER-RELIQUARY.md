# 0.46 — Relic Chamber & Reliquary

Base: `623d048ef32d698264cc3c174c6aea7dac878e67` (accepted 0.45 Enchanted Threshold + Oracle runtime)

## Product goal

Turn two existing software metaphors into magical instruments with memory:

1. focused cards become a **Relic Chamber** rather than a large modal;
2. kept readings become a persistent **Reliquary** rather than an export-options dialog.

Preferred visual anchor remains **RITUAL HYBRID + EXALTED**. ARCANE OS and LIVING BOOK remain fully reversible through 0.44.

## Relic Chamber

The existing `LivingRelicSurface` and `RelicWorkspace` remain authoritative for interaction and canonical/interpretive separation.

0.46 adds a presentation field around them:

- concentric history rings driven only by existing `patina` encounter count;
- project-authored history stages: UNTOUCHED / AWAKENED / TEMPERED / WEATHERED / VENERATED;
- source-qualified edge inscriptions for canonical element / planet / zodiac / letter when the existing reviewed correspondence pack exposes those fields;
- no inscription is manufactured for traditions whose source pack is pending;
- richer chamber frame and card-object depth;
- reduced-motion freezes chamber orbit while retaining static geometry.

The three cards in the main Living Book reading also become direct, keyboard-accessible entrances to the Relic Chamber. This uses the existing `OPEN_CARD` reducer path; it does not create a second card-detail model or bypass existing patina behavior.

Presentation authority:

`PROJECT_AUTHORED_RELIC_HISTORY_PRESENTATION_NOT_SOURCE_FACT`

History-stage names are UI language, not Tarot doctrine.

## Reliquary

`KEEP THIS READING` becomes a real local persistence action.

A kept memory stores:

- exact `reading` object and ReadingRecord;
- the three reading-card layers, including generated exegesis/art where locally available;
- question;
- selected Tarot/style/context references;
- semantic-contract metadata;
- lightweight browse metadata.

It deliberately does **not** duplicate the full 78-card deck for every memory.

When a memory is opened:

1. its catalog references are rebound to current runtime catalog objects;
2. the canonical 78-card deck is rebuilt locally;
3. saved reading-card layers are overlaid on matching canonical IDs;
4. the exact ReadingRecord is restored into the Oracle.

This keeps canonical identity downstream of deck genesis rather than turning the Reliquary into a second deck authority.

## Artwork storage

The Reliquary reuses the existing continuity image infrastructure:

- embedded `data:image/...` payloads are replaced with `grimoire-image://...` references;
- image bytes live in the existing IndexedDB image store;
- localStorage contains only the lightweight Reliquary index/snapshots;
- missing artwork fails soft to `null` while the ReadingRecord survives.

## Reading identity

A memory ID is derived from:

- question;
- spread ID;
- canonical card IDs;
- orientations;
- semantic-contract version/commit.

Keeping the same reading again updates its memory rather than creating unlimited duplicates.

Collection cap: 64 memories.

## Returning Relics

The Reliquary may show cards that recur across kept readings.

Authority:

`PROJECT_DERIVED_READING_HISTORY_NOT_TAROT_FACT`

A recurrence count means only that the same canonical card ID appears in multiple memories. It is not itself a Tarot correspondence or an interpretation.

## Scribe & Export

The previous file tools remain available as secondary operations:

- HTML archive;
- restorable JSON;
- JSON restore;
- Grand Forge.

The primary Archive metaphor is replaced by local memory browsing, but portability is not removed.

## Runtime activation boundary

The pre-activation branch does not modify the two runtime integration files:

- `src/App.jsx`
- `src/tarotBridge/OracleLivingBook.jsx`

Generate the candidate locally with:

```bash
node scripts/apply-0.46-relic-chamber-reliquary.mjs
```

Expected tracked runtime delta is exactly those two files.

## Automated acceptance

```bash
npm run qa:reliquary
node scripts/verify-0.46-relic-chamber-reliquary.mjs
git diff --check
npm run check
```

The QA contract covers:

- ReadingRecord preservation;
- lightweight snapshot (no 78-card deck duplication);
- IndexedDB artwork separation;
- semantic + artwork round-trip;
- history-only recurrence;
- source-qualified Two of Wands chamber inscriptions;
- no invented inscriptions for pending source packs;
- presentation/provider firewall;
- direct Oracle-card → existing `OPEN_CARD` → Relic Chamber wiring.

## Fold acceptance

1. In an active Living Book reading, tap Thesis, Antithesis or Synthesis: that exact card opens directly in the Relic Chamber.
2. The chamber reads as space around a relic, not a plain red dialog; an `OPEN RELIC` affordance is visible on the reading cards.
3. Patina count is labeled as RELIC HISTORY / encounters and still uses existing reducer behavior.
4. Thoth Two of Wands should permit canonical FIRE / MARS / ARIES inscriptions in the chamber field; pending source packs should not.
5. In Oracle, tap KEEP THIS READING: it should save first, then open the Reliquary.
6. The kept reading appears as a memory folio with question, three cards and relation signature.
7. Keep the same reading again: it updates instead of duplicating.
8. Keep another reading sharing a card: RETURNING RELICS may appear with a factual appearance count.
9. OPEN MEMORY restores the exact ReadingRecord, reconstructs a canonical 78-card deck, and its reading cards can again enter the Relic Chamber.
10. Hard refresh preserves the Reliquary.
11. If artwork is unavailable, the memory still opens with canonical semantic data.
12. SCRIBE & EXPORT still exposes HTML / JSON / Grand Forge tools.
13. ARCANE OS and LIVING BOOK remain visually reversible.
