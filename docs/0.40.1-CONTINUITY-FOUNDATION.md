## Product invariant

**A user's Grimoire must become more valuable over time, and expensive local work must survive ordinary application lifecycle events.**

The accepted 0.40 app previously persisted only the separate Spirit-chat key. Deck state, generated card artwork, exegesis, patina and ReadingRecord lived in React memory and could be lost on refresh/process death.

0.40.1 introduces a continuity layer without changing Tarot doctrine or provider contracts.

## Storage architecture

### Lightweight semantic checkpoint

`src/persistence/grimoireStore.js`

Schema:

- id: `grimoire.xr.session`
- version: `1`
- localStorage key: `grimoire_xr_session_v1`

The snapshot retains reducer/session semantics but resets transient UI/work flags on restoration.

Stable checkpoint policy deliberately skips writes while:

- ritual bootstrap is active;
- a card is forging;
- Oracle consultation is running;
- archive compilation is running.

Therefore a process interruption during an expensive job cannot replace the last stable checkpoint with an incomplete transient state.

### Artwork store

Generated ComfyUI artwork currently returns as `data:image/...;base64,...`.

Embedded image payloads are extracted before serialization and stored in IndexedDB:

- database: `grimoire-xr-continuity`
- store: `images`
- semantic reference prefix: `grimoire-image://`

The same data URL appearing in deck/focused-card/reading copies is deduplicated to one image record.

**Invariant:** no `data:image` payload may enter the lightweight localStorage snapshot.

If IndexedDB is unavailable, semantic state is still saved with warnings. On restoration, missing artwork resolves to `null`; card identity, exegesis, ReadingRecord and provenance remain available.

## Crash recovery

`src/ErrorBoundary.jsx`

The root crash boundary provides:

- reload saved session;
- export the lightweight recovery JSON;
- explicit destructive start-clean flow.

It does not mutate Tarot semantics or pretend to repair a failed render.

## Destructive landing protection

The existing logo action directly dispatched `RETURN_TO_LANDING`, which resets reducer state.

The 0.40.1 activator changes that one-click action to an explicit confirmation explaining that the last stable autosave remains available. Blank LANDING state is not persisted, so an accidental return cannot overwrite the previous checkpoint.

A later product-coherence slice may redesign home/navigation; 0.40.1 only removes immediate data-loss behavior.
